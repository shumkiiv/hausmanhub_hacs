Проверяемый код: `ed5f809`. Дата: 2026-09-07.
Результат независимого разбора: к выпуску не готов.
Работающий дом остаётся на Hausman for Home Assistant `1.52.226`.
Миграция, установка и физические команды в этом продолжении не выполнялись.

Тестировщик подтвердил `PYTHONPATH=. pytest -q` на этом commit:
2541 passed, 4 skipped, 1235 subtests passed за 301.89 s. Итог приёмки
BLOCKED. Его первое утверждение о пяти plan-only runtime sources отозвано:
оно относилось к черновому каталогу `tools/managed_scenarios/`, а не к
источникам `custom_components/hausman_hub/managed_scenarios/`.
Перечисленные ниже дефекты проверены на настоящих runtime sources.

## Что установлено

Административный API доступен: scenarios, catalog, health и node-red
возвращают 200. Ответ 403 публичного `/v1/scenarios` для администратора
объясняется разделением ролей: этот маршрут предназначен планшету.
Ослаблять авторизацию не нужно. Свежая read-only проверка насчитала
58 сценариев, 46 включённых, три managed Node-RED контроллера.

После включения владельцем гостиный увлажнитель стал доступен, состояние
`on`, влажность 55. Это наблюдение, а не проверка исполнения климатических
команд. Часовой пояс дома: `Asia/Omsk`.

## Блокирующие дефекты

1. `scenario_service.py:1240` требует существования каждого сценария.
   Пять новых ID отсутствуют в доме, операции создания нет. Их фиктивные
   legacy hashes из повторяющихся цифр не описывают реальные источники.
2. `_registry()` в `test_managed_switch_migration_service.py` создаёт все
   восемь исходных записей из проверяемого manifest. Тест скрывает отсутствие
   настоящего перехода от трёх контроллеров к восьми.
3. Версия квитанции остаётся `managed-switches/2`, но допустимый hash
   изменён. Предыдущая completed-квитанция при её наличии будет отклонена.
   Наличие такой квитанции в доме ещё нужно подтвердить; удалять её нельзя.
4. Туалет, ванная, кладовка и кабинет не возвращают обязательный `trace.title`.
   Настоящий `NodeRedScenarioBackend.async_plan()` отвергает ответ.
   Прямой JavaScript-тест эту проверку обходит.
5. Фильтр атрибутов снимка не пропускает `current_position` для штор.
   Тесты подставляют положение напрямую и скрывают пустой настоящий снимок.
6. Ванная принимает состояние световых линий за присутствие и включает
   вторую линию с вытяжкой. Кабинет принимает наружный lux за присутствие.
   Туалет включает оба источника без взаимоисключения и задержки вытяжки.
   Кладовка не выключает свет после двух минут отсутствия.
7. Шторы при sunrise формируют пустой план. Ручное «открыть все» из позиции
   0 отправляет 0. Долговечной ручной защёлки нет. Закрытие кабинета до 0
   не сохраняет прежний безопасный порог до проверки калибровки.
8. Из `scenario_controls.py` исполнитель использует только
   `OccupancyEvidence`. Новые расписания, относительное снижение яркости,
   ручное владение, пределы штор и проверка питания не подключены полностью.
   Старые три JavaScript-контроллера не реализуют новые временные правила.

Пробы были программными, без физического воздействия. Подтверждены пустой
sunrise-план, четыре команды 0 при ручном открытии закрытых штор, включение
второй линии ванной и отсутствие выключения кладовки по таймеру.

## Новый порядок исправления

1. Сохранить независимый снимок настоящих definitions, revisions, enabled,
   sources, bindings и пересекающихся автоматизаций HA. Составить матрицу
   «перенести / сохранить / отключить дубль». Не выводить секреты. Воду и
   автоматы исключить по точным целям, включая вложенные сценарии.
2. Разделить миграцию на `create`, `replace`, `disable`, `preserve`.
   Проверять отсутствие новых ID и точную исходную версию старых. Создавать
   definitions, triggers и отключённые flow. Ввести новую версию миграции
   с явным обновлением проверенной старой квитанции.
3. Довести кладовку сквозным путём: настоящий снимок, OR датчиков,
   `async_plan`, разрешённые действия, подтверждённое владение светом,
   непрерывное отсутствие 120 секунд, выключение. Вытяжку не назначать
   наугад: её точная привязка ещё не найдена.
4. Подключить общий координатор света с долговечным владением, временем
   отсутствия, ручной защитой и отменой старых переходов. Затем реализовать
   разные расписания тамбура и малого коридора.
5. Перенести душевую, туалет, ванную и кабинет по настоящим условиям.
   Ванная автоматически управляет вытяжкой, не включает световые линии.
6. Шторы выполнить отдельно: правильные атрибуты, ручное открытие, sunrise,
   долговечная защёлка, пределы общего пути команд. Сначала подтвердить
   аппаратную шкалу и способы обхода серверного ограничения. Владелец
   согласен визуально наблюдать калибровку, но движения ещё не запрашивались.
7. Отдельно завершить климатическую полноту и задержки, интервью душевой,
   редактируемые настройки и физические проверки с голосовыми объявлениями.

## Критерии допуска к следующему выпуску

- Исходный fixture содержит три managed-контроллера и настоящие старые
  правила, а не восемь записей из нового manifest.
- Переход к восьми контроллерам и обновление старой квитанции проходят.
- Сбой на каждом шаге миграции не оставляет одновременно включённые старые
  и новые правила. Откат сохраняет последующие изменения пользователя.
- Все восемь sources проходят настоящий `async_plan` и фильтрацию снимка.
- Яркость 80 снижается до 72 за 300 секунд; 5 поднимается до 80 за 30
  секунд только при пределе 80; предел 5 не превышается.
- Вечер начинается не позже 21:00. Тамбур не включает основной свет после
  23:00, малый коридор не включает свет после 23:30 до sunrise.
- Расписание не включает погашенный свет; ручной свет не присваивается
  автоматике. Проверены unknown, один/два датчика, restart, отмена перехода
  и неподтверждённое питание.
- Четыре шторы проходят sunrise, ручное открытие из 0, пределы, restart и
  очистку ручной защёлки только следующим sunrise.
- После успешного тестировщика проходят ревью и аудит безопасности.
  Только затем допустимы выпуск, установка и физическая приёмка.

Нынешний зелёный набор тестов без этих проверок не доказывает готовность.
